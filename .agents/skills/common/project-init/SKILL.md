# 项目规范初始化

## 触发条件

当用户输入以下类似指令时，调用此技能：

- "初始化项目规范"
- "初始化项目"
- "初始化当前项目"
- "初始化当前项目规范"
- "生成项目概述"
- "填写 01 和 03"
- "分析项目技术栈"
- "生成项目结构文档"
- "根据项目生成自定义规则"
- "自定义 04/05/06/07/09"
- "生成项目规则"
- "project-init"
- "project init"

## 前置要求

1. 当前工作区必须是一个前端项目（存在 `package.json`）。
2. `.agents/rules/` 目录已存在（通过 `install.sh` / `install.ps1` / `npx init` 或手动创建）。
3. 若 `context/` 目录不存在，可由本技能创建。
4. 规则生成范围由两类信号共同决定：
   - `.agents/rules/` 中规则文件是否缺失
   - `.ai-spec/manifest.json.local_preferences.project_init.custom_rules` 中是否声明了需要按项目自定义生成或刷新的规则

## 执行目标

本技能的固定目标是：

- 始终生成或刷新：
  - `.agents/rules/01-项目概述.md`
  - `.agents/rules/03-项目结构.md`
  - `context/PROJECT.md`
- 若项目已安装 OpenSpec（存在 `openspec/`），同步 `openspec/project.md` 中的项目概述
- 对于安装时选择了“根据项目自定义”的规则，按项目事实生成或刷新：
  - `04-组件规范.md`
  - `05-API规范.md`
  - `06-路由规范.md`
  - `07-状态管理.md`
  - `09-样式规范.md`

## 完成标准（强约束）

以下条件必须同时满足，才算本次 `project-init` 完成：

1. `01-项目概述.md`
2. `03-项目结构.md`
3. `context/PROJECT.md`
4. 若存在 `openspec/`，则 `openspec/project.md` 已同步
5. 若 `.agents/rules/` 下缺失 `04/05/06/07/09` 中任意文件，则这些缺失项必须在本次执行中一并补生成
6. 若 `.ai-spec/manifest.json.local_preferences.project_init.custom_rules` 中包含 `04/05/06/07/09` 中任意规则，则这些规则即使文件已存在，也必须在本次执行中按项目事实刷新

也就是说：

- **如果待生成列表非空，只写 `01/03 + PROJECT` 视为未完成**
- **不能在摘要里只说“后续再补 04/05/06/07/09”**
- **不能只分析、不落盘**
- **不能只生成其中一部分缺失规则后就结束**

## 执行步骤

### 第零步：确定规则生成范围

先检查 `.agents/rules/` 目录下的规则文件，确定哪些规则需要生成：

**必定生成/刷新**

- `01-项目概述.md`
- `03-项目结构.md`

**按需补生成或刷新**

| 编号 | 文件名 | 说明 |
|------|--------|------|
| 04 | `04-组件规范.md` | 组件结构、目录组织、编写约定 |
| 05 | `05-API规范.md` | 接口目录、请求封装、命名、错误处理 |
| 06 | `06-路由规范.md` | 路由配置、懒加载、守卫、目录结构 |
| 07 | `07-状态管理.md` | Store 目录、模块划分、编写规范 |
| 09 | `09-样式规范.md` | 样式方案、主题变量、全局样式 |

**判断逻辑**

- 先检查 `.ai-spec/manifest.json`：
  - 若存在 `local_preferences.project_init.custom_rules`，则其中列出的规则记为 `待刷新列表`
- 再检查 `.agents/rules/`：
  - 若 `04/05/06/07/09` 中某个文件在 `.agents/rules/` 下不存在，则该规则记为 `待生成列表`
- 若某条规则同时出现在 `待刷新列表` 与 `待生成列表`，按“生成或刷新”统一处理
- 若某条规则文件已存在，且也不在 `待刷新列表` 中，则默认视为标准规范已落盘或用户已手动维护，不覆盖

完成这一步后，立即形成一份明确的 `本轮写入清单`：

- 固定写入：
  - `.agents/rules/01-项目概述.md`
  - `.agents/rules/03-项目结构.md`
  - `context/PROJECT.md`
- 条件写入：
  - `openspec/project.md`（仅当 `openspec/` 存在）
  - `待生成列表` 中所有缺失的 `04/05/06/07/09`
  - `待刷新列表` 中需要按项目事实重写的 `04/05/06/07/09`

后续执行必须以这份 `本轮写入清单` 为准，逐项落盘，不得遗漏。

### 第一步：采集基础项目信息

依次读取以下信息，提取稳定事实：

**1.1 `package.json`**

至少提取：

- UI 框架：`react` / `vue` / `angular`
- 类型系统：`typescript` 是否为项目依赖
- 构建工具：`vite` / `webpack` / `next` / `nuxt`
- 路由管理：`react-router*` / `vue-router`
- 状态管理：`zustand` / `pinia` / `redux` / `mobx`
- 组件库：`antd` / `element-plus` / `@mui/*`
- 样式方案：`tailwind` / `sass` / `less` / CSS Modules / scoped 等线索
- HTTP 请求：`axios` / `fetch` / 自有请求封装
- 常用工具：`ahooks` / `@vueuse/core` / `lodash*` / `dayjs` 等

**1.2 `README.md` / 已有项目说明（如存在）**

提取稳定背景：

- 项目定位
- 业务目标
- 核心术语
- 架构关键词
- 明确的边界或非目标

若仓库无稳定说明，则只保留可确认事实，不编造背景。

**1.3 扫描 `src/` 目录结构**

至少确认：

- 顶层目录列表及用途推断
- 入口文件（如 `main.ts` / `main.tsx` / `App.vue` / `App.tsx`）
- 页面目录模式（`views/` / `pages/`）
- 路由组织模式（文件路由 / 配置路由 / 当前无路由骨架）

**1.4 检测项目类型**

根据现状判断：

- SPA
- SSR/SSG
- 微前端
- 组件库/工具库
- Monorepo

**1.5 判定 TypeScript / JavaScript**

- 若 `package.json` 的 `dependencies` 或 `devDependencies` 中存在 `typescript`，视为 TypeScript 项目
- 否则按 JavaScript 项目处理

### 第二步：仅对待生成/刷新规则做深度扫描

只扫描 `待生成列表 + 待刷新列表` 中对应的能力域，避免全量重扫。

**若待生成 04-组件规范**

- 扫描 `src/components/`、`src/views/*/components/`、`src/pages/*/components/`
- 随机读取 2-3 个组件文件，确认：
  - Vue：`<script setup>` / `lang="ts"` / `defineProps` / `defineEmits`
  - React：函数组件 / Props 接口 / JSX/TSX
- 归纳组件目录组织方式、拆分边界、组件库使用方式

**若待生成 05-API规范**

- 扫描 `src/api/`、`src/services/`、`src/request/`
- 读取 2-3 个接口文件或请求封装文件，归纳：
  - 请求库与统一封装入口
  - 命名模式
  - 类型落点（如 `src/api/types/`）
  - 错误处理模式

**若待生成 06-路由规范**

- 扫描 `src/router/`、`src/routes/` 或文件路由目录
- 读取现有路由配置，归纳：
  - 路由入口与模块拆分
  - 懒加载写法
  - `meta` 使用情况
  - 导航守卫
  - 页面目录与路由的映射方式

**若待生成 07-状态管理**

- 扫描 `src/store/`、`src/stores/`
- 从 `package.json` 和现有代码确认状态库
- 读取 2-3 个 store 文件，归纳：
  - 编写方式
  - 命名约定
  - 模块拆分方式
  - 是否使用持久化

**若待生成 09-样式规范**

- 统计样式文件后缀分布
- 检测 Vue SFC 的 `<style scoped>` / `module` / 无限定
- 检测是否存在 `src/styles/` 或全局样式入口
- 归纳 CSS 变量、主题 token、组件库主题覆盖、Tailwind 使用情况
- 检测硬编码颜色与主题变量的使用倾向

### 第三步：生成或刷新 01-项目概述.md

在 `.agents/rules/` 下生成（或刷新）`01-项目概述.md`，要求：

- 项目定位一句话描述必须来自可确认事实
- 技术栈表只写项目实际安装和实际使用的技术
- TypeScript / JavaScript 分支必须按项目实际依赖区分
- 私有包或公司内部包需单独标注用途
- 不得把未经确认的业务背景写成既定事实

### 第四步：生成或刷新 03-项目结构.md

在 `.agents/rules/` 下生成（或刷新）`03-项目结构.md`，要求：

- 目录树必须反映 `src/` 下的实际目录
- 每个目录用途需根据 2-3 个样本文件归纳，而不是猜测
- 如果项目存在路由目录、页面组件目录、Mock 策略，写清对应放置规则
- 所有示例文件扩展名必须跟仓库实际一致，不要写死 `.ts`

### 第五步：生成或刷新 `context/PROJECT.md`

在 `context/` 下生成（或刷新）`PROJECT.md`，内容只保留稳定项目上下文：

- 项目定位
- 技术栈摘要
- 关键规范入口
- 业务目标
- 核心术语
- 架构概览
- 非目标

填写要求：

- `项目定位` 与 `01-项目概述.md` 保持一致
- `技术栈摘要` 只写可确认事实
- `业务目标 / 核心术语 / 非目标` 无法确认时明确写 `待补充`
- 不把某次任务的默认假设、页面落点、登录方式等运行态信息写进来

### 第六步：同步 `openspec/project.md`

若项目存在 `openspec/`：

- 若 `openspec/project.md` 已存在，只更新其中 `## 项目概述` 段落，使其与 `01-项目概述.md` 的项目定位一致
- 若 `openspec/` 已存在但 `openspec/project.md` 缺失，可创建最小 `project.md`，至少包含：
  - `# Project`
  - `## 项目概述`
  - 与 `01-项目概述.md` 一致的一句话定位
- 不修改 `project.md` 中其他无关章节

若项目未安装 OpenSpec（不存在 `openspec/`），跳过此步骤。

### 第七步：补生成缺失的自定义规则

仅对 `待生成列表` 中的规则执行本步骤。每个规则都要基于仓库事实生成，不得照搬标准模板内容。

#### 7A. 生成 `04-组件规范.md`

必须覆盖：

- 当前组件结构写法
- 组件目录组织方式
- 页面专属组件与通用组件的放置规则
- Props / Emits / 回调 / 事件的现状约定
- 拆分边界和不可违背的规则

若项目当前没有独立组件目录，也要明确写清“当前不存在 + 推荐落点 + 后续新增约束”。

#### 7B. 生成 `05-API规范.md`

必须覆盖：

- 接口目录和请求封装入口
- API 与类型文件的推荐落点
- 函数命名模式
- 错误处理模式
- 页面/组件禁止直接请求的约束（若项目已有这类惯例）

若项目还没有统一 API 层，要写清当前现状、推荐落点和后续统一约束。

#### 7C. 生成 `06-路由规范.md`

必须覆盖：

- 路由入口
- 路由模块或文件路由组织方式
- 页面目录与路由目录的对应关系
- 懒加载要求
- `meta` / 守卫现状与约束

若项目当前没有路由骨架，要明确写清“当前不存在 + 推荐骨架 + 新增页面时的落点约束”。

#### 7D. 生成 `07-状态管理.md`

必须覆盖：

- 当前状态库
- store 目录与命名约定
- 模块拆分方式
- 在组件中使用 store 的方式
- 持久化现状

若项目没有全局状态目录，要明确“当前无全局状态层 + 何时才需要新增 + 推荐落点”。

#### 7E. 生成 `09-样式规范.md`

必须覆盖：

- 当前样式方案
- 主题变量或主题 token 的现状
- 全局样式入口
- scoped / CSS Modules / Tailwind / Less / Sass 的实际使用规则
- 禁止硬编码颜色值或主题偏离的约束（若项目有主题体系）

若项目暂无主题变量，也要写清当前现状、推荐入口和后续新增样式时的基本约束。

### 第八步：用户确认

在真正写入前，先向用户给出简要确认摘要，至少包含：

1. 检测到的技术栈
2. 检测到的目录结构
3. `PROJECT.md` 中的项目定位和关键规范入口
4. 若存在自定义规则待生成，逐项说明将补哪些规则
5. 若存在 OpenSpec，同步到 `openspec/project.md` 的项目定位描述

确认问题建议使用：

> 以上信息是否准确？若无异议，我将写入 01/03、PROJECT，以及当前缺失的自定义规则。

一旦用户确认继续，必须按 `本轮写入清单` 一次性完成全部写入；不要只写 `01/03` 后提前结束。

## 注意事项

- `01-项目概述.md`、`03-项目结构.md`、`context/PROJECT.md` 可以按当前项目事实刷新
- `04/05/06/07/09` 仅在文件缺失时补生成；若文件已存在，不覆盖
- 当 `待生成列表` 非空时，`04/05/06/07/09` 的缺失项属于本次必做项，不是可选项
- 自定义规则必须基于项目实际代码、目录和依赖归纳，严禁照搬通用模板
- 如果项目不是前端项目（无 `package.json`），应提示用户手动填写并提供空白模板方向
- 若 `openspec/` 不存在，不强制创建 OpenSpec，只跳过 `openspec/project.md` 同步
- 禁止把“已检测到待生成规则”只写进摘要或建议，而不实际写入对应文件
